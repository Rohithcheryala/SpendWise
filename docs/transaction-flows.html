Transaction event timelines

Every flow as the chronological sequence of events: call → job → API call → DB row — with the business reason on each node.

Node colors: CALL function/API invocation   READ db read   WRITE db row saved   DELETE rows removed   BRANCH decision point   UI side effect.
All money in paise (Long). No entry kind is ever stored — every kind is derived from its lines at read time.

1 · Bank SMS → buffer entry

POST /ingest — SmsBroadcastReceiver (live) or SmsSyncWorker (45-min poll) → parser → IngestionService.ingestSms(facts) → LedgerService.ingest SmsParseFacts { sender, bank, last4, smsAccountKind, idKinds?, amountPaise, direction, counterpartyRaw?, refId?, rawText, happenedAt?, occurredOn }
Text.smsHash(sender, rawText) CALL
Builds the stable idempotency key for this exact SMS.
ledger.findEntryByDedupeHash(hash) READ entry_provenance BRANCH
Hit → return Duplicate(entryId). FLOW ENDS. This one check is why the live receiver, the periodic worker and a manual inbox pull can all race on the same SMS without double-booking.
findAccount(bank, last4, smsAccountKind, idKinds) READ account_identifiers READ accounts
Job: identifiers active with value=last4 → channel filter (idKinds: a card number can't hijack an account match) → account must be active, non-system, bank contains-match, kind reachable via KIND_BRIDGE (savings→{available,asset,cash}, credit_card→{liability,asset}).
no account matched BRANCH
account = null → the orphan path. The entry will park on the unmatched pot (step 6) — it never books against a wrong account. User classifies it later (§9 assignAccount) or §1b claims it.
Text.extractVpa(rawText) + contacts.resolveContactName(rawText) CALL READ contacts
UPI handle = the strongest cross-source key; a phone-prefixed handle gets the saved contact's name as the friendly display.
counterparties.findByAny(userId, vpa, counterpartyRaw) READ counterparty_aliases
Alias lookup — one payee, many raw strings (VPA, narration slug).
miss → resolveOrCreate() WRITE counterparties WRITE counterparty_aliases
First-seen payee: row with party_type=merchant, then the raw string saved as a normalized alias (source upi/sms) so the next message resolves without this step.
ledger.ingest(IngestRequest) CALL
Intent defaults by direction: IN→income, OUT→expense. accountId ?: systemAccount(UNMATCHED) (get-or-create, READ/WRITE accounts). contraLine(): opposite leg = system category Unclassified/Uncategorized income (get-or-create, READ/WRITE categories).
db.withTransaction → entryDao.insert + entryLineDao.insertAll WRITE entries WRITE entry_lines ×2
Row: status=buffer, source=sms. Lines: [±amt → account (or pot), ∓amt → category] — balanced by construction. Buffer = invisible to every balance until proven (§2 merge or manual confirm).
provenanceDao.insert WRITE entry_provenance
raw_text (the SMS), dedupe_hash (step 1), bank_ref, and parsed_facts = "bank|last4|accountKind" — facts frozen now, so orphan claiming (§1b) re-matches without re-parsing raw text (parser drift can't rewrite history).
tryMergeQrScanBuffer(entryId) CALL
A QR scan for this payment may already be waiting in buffer → continue in §2, step 8.
notification + watermark UI
Live path only: TransactionNotifier posts the parsed-capture alert; app_metadata.last_sms_sync advances for inbox pulls.

1b · Orphan claiming (retroactive attach)

PUT /entries/{id}/account (bulk) — account created/edited → claimOrphansForAccount(accountId)
guard BRANCH
Account has bank + ≥1 active identifier? No → return 0.
scan orphans READ entry_lines, entries, entry_provenance
All entries with a line on the unmatched pot, source=sms, not voided, with full parsed_facts.
re-run findAccount(frozen facts) → matched? WRITE entry_lines.account_id
Matches on the frozen facts, never re-parsed raw text. Attach-only, never detach — safe to re-run on every account edit.

2 · QR Scan & Pay → merge → confirmed (one chronological story)

POST /entries or POST /ingest — ScannerViewModel.recordQrPayment { vpa, payeeName, amount, note, tags[], accountId?, categoryId?, upiUri } — accountId is OPTIONAL: the payment can fail & be retried elsewhere; the bank SMS decides the account
counterpartyService.resolveOrCreate(userId, rawName = vpa, aliasSource = "upi") READ counterparty_aliases WRITE counterparties + aliases
The VPA is the strongest key: if an SMS from this payee was ever ingested, the same row is reused — that's what lets the merge (step 8) bind the two entries to one party.
debitAccountId = accountId ?: systemAccount(UNMATCHED).id READ accounts
Nothing picked? park on the pot — the merge re-points it to the real account later (step 8).
categoryId picked? BRANCH
Chooses the write shape — both produce the same buffer entry.
A: ledgerApi.createEntry(lines = [−amt→account, +amt→category], status=buffer, source=qr_scan) WRITE entries + entry_lines ×2
Category leg written directly — nothing to re-classify later.
B: ledgerApi.ingest(intent=EXPENSE, dedupeHash = md5("qr|vpa|amt|note|minute-bucket")) WRITE entries + entry_lines ×2 + entry_provenance
rawText = the upi://pay URI. The minute-bucketed hash stops a double-tap from booking twice.
inboxRepository.refreshBuffer() UI
Badge/list update immediately. The entry sits in buffer — invisible to every balance, waiting for proof.
time passes — the bank SMS lands → §1 steps 1–5 run for the SMS entry
tryMergeQrScanBuffer(smsEntryId) CALL READ entries, entry_lines
Candidates: status=buffer, source=qr_scan, not voided, created ≤ 30 min ago. Match = same direction AND amountsMatch(±1% symmetric, +2% increase-only) — the increase band absorbs last-step convenience fees; a decrease beyond ±1% never matches (a different payment).
exactly one match? BRANCH
0 or 2+ matches → both entries stay in buffer; the ambiguity surfaces in the inbox for the user. Never guesses.
merge WRITE entries WRITE entry_lines DELETE entry_lines + entries (QR row)
SMS entry → confirmed. Tags unioned. SMS adopts the QR's real account only if the SMS was orphaned; adopts the QR's category only if its contra is still Unclassified. QR entry deleted — one payment, one transaction. The SMS amount wins (bank's actual debit, fee included, is the truth).

3 · Manual category entry (expense / income)

POST /entries — Type = Category → TransactionViewModel.saveCategoryEntry → LedgerService.createEntry CreateEntryRequest { occurredOn, lines[], status=confirmed, source=manual, counterpartyId?, note?, tags[] } — lines composed by the caller: [±amt → account, ∓amt → category]
strict mode? BRANCH
Setting on → entry needs ≥1 tag, else rejected before any write.
editing? → voidEntry(oldId, "edited") WRITE entries.voided_at
Edits never mutate history — old row soft-deleted (audit trail kept), new row written.
createEntry → validateLines → db.withTransaction WRITE entries + entry_lines ×2
Invariants checked: ≥2 lines, sum = 0, one target per line. Born confirmed — a human typed it, no proof needed, balances see it immediately. Counterparty is optional and rides on the header.

4 · Transfer (self, intra-account)

POST /ingest/transfer — Type = Transfer (or ATM-withdrawal SMS) → LedgerService.ingestTransfer { amountPaise, fromAccountId, toAccountId, occurredOn, status, source, rawText?, dedupeHash?, bankRef?, balanceAfterPaise?, note? }
guard BRANCH
fromAccountId == toAccountId → rejected: moving money to itself is not a movement.
createEntry(lines = [−amt → from, +amt → to]) WRITE entries + entry_lines ×2
No counterparty, no category — two account legs is the whole story. Balance moves between pools; net worth untouched.
provenance (if rawText/dedupeHash/bankRef present) WRITE entry_provenance
read-back: buildView READ entries + entry_lines
Sees ≥2 user account legs, no categories → kind TRANSFER, toAccountId = the positive leg. Derived, never stored.

5 · Loan given / loan repayment

POST /ingest with intent = loan | loan_repayment — Type = Loan → saveLoan (direction OUT→loan, IN→repayment) → LedgerService.ingest IngestRequest { amountPaise, direction, occurredOn, accountId (required, real), counterpartyId (required, the person), intent, tags, status=confirmed, source=manual, note }
contraLine(intent) → WRITE entries + entry_lines ×2
Primary = ±amt on the user's account; contra = ∓amt on sys-loans-1 (RECEIVABLE) carrying the line-level counterpartyId. Gave a loan = pot up; repayment = pot down.
read-back: buildView READ
Receivable line present → recv > 0 ? LOAN : LOAN_REPAYMENT.
friendsOutstanding() READ entry_lines, counterparties
Net per person on the pot, confirmed non-void lines only; positive = they owe you; settled omitted. The loan form's "They currently owe you ₹X" check figure reads this.
Sharp edge: the pot is per-person only via the line's counterparty_id. A loan line without one is invisible to the Friends ledger.

6 · Split — carving friends' shares out of a paid entry

POST /entries/{id}/split — transaction detail, split editor → LedgerService.splitEntry SplitRequest { shares: List<SplitShare(counterpartyId, amountPaise)>, groupId? } — target must have a single category leg
locate the category leg READ entry_lines
categoryId != null && bucketId == null, exactly one — else reject. Entry is loaded with its lines inside one db.withTransaction.
per share: shrink category leg + append receivable leg WRITE counterparties.party_type=person
Category line amountPaise −= share (going negative → "shares exceed the paid amount"); new line +share on sys-loans-1, counterpartyId = person. ensurePartyType(person) — shares surface on the Friends ledger.
validateLines CALL
Rewritten set must still sum to zero — balance preserved by construction.
entryLineDao.deleteByEntry → insertAll(rewritten) DELETE + WRITE entry_lines WRITE entries.group_id
Lines replaced as a set inside the transaction; group link updated if passed. Kind now reads SPLIT (receivable + expense lines both present).

7 · Opening balance

PUT /accounts/{id}/opening-balance — account create / balance edit → recordOpeningBalance
find prior opening entries READ entry_lines
Entries with lines on both this account and sys-openeq-1 (set intersection).
delete each prior DELETE entry_lines, entry_provenance, entries
Replacement strategy — editing an opening balance removes the old baseline entry entirely.
opening == 0? BRANCH
Stop — replacement with zero means removal.
createEntry([±opening → account, ∓opening → sys-openeq-1]) WRITE entries + entry_lines ×2
Sign flipped for liability accounts (owed amount). status=confirmed, note "Opening balance", dated onDate ?: reconciledThrough. Idempotent by construction.

8 · Bucket allocation

PUT /buckets/{id}/allocation — bucket create / allocation edit → recordBucketAllocation
delete prior allocations (by note "Bucket opening allocation") DELETE entry_lines, entry_provenance, entries
manualAllocationPaise == 0? BRANCH
Stop — zeroing the allocation removes the baseline.
createEntry([−alloc → account (no bucket), +alloc → SAME account with bucketId]) WRITE entries + entry_lines ×2
A self-transfer that nets zero on the account: the general pool "moves" into the sub-pot, so bucketValue becomes purely the sum of lines tagged with that bucket. Kind reads ALLOCATION.

9 · Lifecycle operations

POST /entries/{id}/confirm — confirmEntry(id, extraTags)
load entry + lines READ entries, entry_lines, accounts
real account leg present? BRANCH
No → reject "confirm requires account". An orphan can't be confirmed into existence — booking a payment against no real account is forbidden.
promote WRITE entries.status=confirmed (+ tags union)
From this moment every balance computation sees the entry. extraTags union order-preserving, deduped — same rule as the QR merge.
PUT /entries/{id}/account — assignAccount(entryId, accountId)
guards BRANCH
Account must exist and not be a sys- system account; entry must have exactly one pure account leg (account, no category/bucket) — else reject.
re-point WRITE entry_lines.account_id
The manual fix for an orphaned/mis-matched SMS from the inbox.
DELETE /entries/{id}/void — voidEntry(id, reason?)
soft-delete WRITE entries.voided_at + voided_reason
Idempotent (already voided → no-op). Voided rows drop out of every balance, list and merge candidate. Edits use void + rewrite — the ledger keeps an audit trail instead of mutating history.
DELETE /entries/{id} — deleteEntry(id)
hard delete, one transaction WRITE entries (clear linked_entry_id) DELETE entry_lines → entry_provenance → entries
Pointers cleared first so nothing dangles on the removed id.
